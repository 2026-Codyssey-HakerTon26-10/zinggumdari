# 징검 KNN·인프라 구현 현황 및 미완료 사항 보고서

작성 기준일: 2026-11-01 (한국시간)

## 1. 요약 판단

GPU KNN을 독립 서비스로 실행하고 일반 서버에서 인증된 요청을 보내는 기반은 구축되어 있다. EC2를 통한 Ncloud 검색 API의 외부 HTTPS 접근도 실제 응답으로 확인했다. 그러나 Render의 실사용자 프로필이 GPU 검색과 정책 후보 생성으로 이어지는 전체 추천 경로는 완료 증거가 없다.

따라서 현 상태는 ‘GPU 이웃 검색 서비스와 네트워크 기반 구축·부분 검증 완료, 운영 추천 통합 미완료’로 평가한다. 완료 비율을 숫자로 제시하지 않는다. 작업별 난이도와 완료 기준이 다르고, 로컬 코드 존재와 실제 배포 완료를 동일하게 셀 수 없기 때문이다.

추가 구현은 시간 제약에 따라 수행하지 않았으며, 본 보고서는 현재 성과와 남은 범위를 기록하는 문서다.

## 2. 판단 기준과 증거 범위

| 상태 | 의미 |
|---|---|
| 실행 확인 | 사용자가 제공한 서버 명령·응답에서 동작이 확인됨 |
| 코드 존재 | 로컬 파일에서 구현을 확인했지만 운영 호출·배포는 별개 |
| 미완료 | 현재 구성에 필요한 연결 또는 산출물이 없음이 확인됨 |
| 미확인 | 완료 여부를 판정할 실행 결과·설정 증거가 부족함 |

서버의 라이브 상태를 이번 작성 시점에 다시 조회한 것은 아니다. 사용자가 공유한 마지막 실행 결과를 기준으로 한다. Render DB 사용은 사용자 확인에 근거하며, 실제 회원 행을 직접 조회한 결과는 아직 없다.

## 3. 현재 구성과 실제 경로

```text
[운영 회원가입]
사용자 → Vercel /api/backend/auth/signup
       → Render FastAPI → Render PostgreSQL

[별도 검증된 공개 검색]
외부 PC → api.choboim.p-e.kr (EC2 HTTPS)
        → EC2 loopback:18081 → 역방향 SSH 터널
        → Ncloud 일반 서버:8080 → FastAPI:8000

[별도 검증된 GPU 호출]
Ncloud 일반 서버 → 내부 TLS:8443 + 인증
                 → GPU API:8001 → CuPy/L4 → 이웃 반환

[연결 완료 증거 없음]
Render의 실사용자 추천 요청 → Ncloud GPU → 최종 추천 화면
```

Vercel의 `NEXT_PUBLIC_API_BASE`는 사용자 확인 당시 Render 주소였다. `next.config.ts`의 `/api/backend/*` rewrite가 이 값을 목적지로 사용한다. 별도 `vercel.json`에는 `/api/health`, `/api/search`의 EC2 전달 설정이 있다. 코드의 두 경로가 존재한다는 사실만으로 실제 화면의 검색·추천이 어느 경로를 사용하는지 확정하지 않는다.

## 4. 구성 요소별 구현 현황

| 영역 | 구현 및 증거 | 판정과 제한 |
|---|---|---|
| 일반 서버 | Ncloud 10.1.1.18, FastAPI systemd 실행, localhost health 정상 | 실행 확인 |
| 일반 서버 PostgreSQL | 16.14, localhost:5432, zinggum DB·앱 역할 생성 | 설치·접속 확인. 마지막 조회에서 사용자 테이블 0개 |
| GPU 서버 | Ncloud 10.1.2.18, NVIDIA L4, 드라이버 580.159.04 | 장치 인식 확인 |
| CuPy 계산 API | `/health`, `/ready`, `/metadata`, `/neighbors` 구현 | 서버 준비 상태와 계산 비교 실행 확인 |
| 데이터 | 전체 10,000행 중 pool 9,000행·32차원 로딩 | ready 응답 확인. Render 회원 데이터와 별개 |
| 전처리 | `stage2`, `query_vector` 구현 존재 | Render DB 필드와 운영 연결 미확인 |
| CPU 추천 | `neighbors`, `recommend` 구현 존재 | 정책별 해당 표·개인 판정 입력의 운영 준비 상태 미확인 |
| GPU 내부 보호 | 일반 서버 IP 허용, TLS 인증서 검증, Bearer 인증 | 비허용 출발지 403, 미인증 요청 401 확인 |
| GPU 프로세스 운영 | systemd 서비스 구성 | 실행·재시작 후 준비 확인. 전체 호스트 재부팅 검증 미확인 |
| EC2 공개 진입점 | Let’s Encrypt, Nginx HTTPS, 일반 서버발 역방향 SSH | 외부 health·search 정상 응답 확인 |
| 터널 계정 제한 | 공개키 인증, remote forwarding, loopback 18081, 셸 제한 | 설정 검사·loopback 수신 확인 |
| 터널 자동 시작 | 자동 재연결 서비스와 enable 명령 제공 | 실제 부팅 자동 시작 등록·재부팅 복구 결과 미확인 |
| 회원가입 | Vercel→Render 요청 201, Render PostgreSQL 사용 확인 | 실제 저장 행 조회는 미확인. Ncloud 저장 아님 |
| 로컬 백업 | 일반·GPU 암호화 백업, timer, 복호화/아카이브 검사 | 실행 확인. 일반 DB 복원 시험 당시 앱 테이블 0개 |
| 외부 백업·알림 | 외부 복사용 절차 제공 | 복사 완료·외부 알림 전달 증거 없음 |

## 5. 확인된 실행 결과

### GPU 준비 상태

```json
{
  "knn_ready": true,
  "version": "671fd425a631265b07ca8096e01f5b7b9448e71cfe37e9ac95a367b641d66d23",
  "rows": 9000,
  "dimensions": 32
}
```

### CPU/GPU 비교

```text
PASS: 18 sampled real-pool CPU/GPU comparisons; not a full recommendation evaluation
```

여기서 real-pool은 해당 비교 도구가 실제 배포용 pool을 사용했다는 뜻이다. 비교 인구가 실제 가입자라는 뜻은 아니다. 18건의 계산 비교는 전체 입력 공간의 정확도, 추천 적합성, GPU 속도 우위를 증명하지 않는다.

### 공개 API

Mac에서 `https://api.choboim.p-e.kr/api/health` 요청이 `{"status":"ok"}`를 반환했고, `/api/search?q=버팀목`은 정책 검색 결과 20개를 반환했다. 검색 응답에는 `judge: fake`가 있었다. 이는 실제 판정 엔진의 완료를 입증하지 않으며 검색 응답만으로 GPU 호출을 증명할 수도 없다.

### 장애 분리

GPU 서비스 중단 시 GPU 경로는 502, 일반 API health는 200인 결과가 확인됐다. 이는 일반 API의 단순 생존 확인이 GPU와 분리되어 있다는 증거다. GPU 장애 시 CPU 추천으로 자동 전환됐다는 증거는 아니다.

## 6. 현재 미완료·미확인 기능

### A. Render 프로필과 입력 벡터의 연결

전처리 함수 자체는 존재한다. 그러나 Render 프로필 조회, 여러 테이블 결합, `birth_date`→`birth_year` 처리, 범주값 변환, scale·열 순서·기준연도 일치를 실제 요청에서 확인하지 못했다. 기존 설명에서 전처리 기능 전체가 없는 것처럼 표현한 부분은 ‘운영 연결이 확인되지 않았다’로 정정한다.

### B. Render에서 GPU까지의 호출 경로

현재 EC2는 `/api/health`, `/api/search`만 공개한다. 추천용 POST 중계, Render용 서버 간 인증, 일반 서버의 추천 처리 어댑터, Render 호출부는 완료 증거가 없다. 기존 GPU 토큰을 브라우저에 넘기는 방식으로 해결해서는 안 된다.

### C. GPU 결과를 정책 후보로 변환

GPU API는 이웃 ID·거리만 반환한다. 로컬 CPU 추천 함수는 있지만 내부에서 CPU 이웃 검색을 수행한다. GPU의 source_row·user_id를 정책 해당 여부 행렬에 매핑하고, 데이터·규칙 버전을 일치시키며, GPU 결과를 추천 집계에 전달하는 연결은 별도 구현·검증 대상이다.

### D. 실제 규칙 판정과 유효한 정책 정보

추천 함수는 정책별 해당 여부 행렬과 본인 판정 결과를 요구한다. 필요한 산출물의 최신성·완전성·운영 생성 여부는 확인되지 않았다. `judge: fake`인 Ncloud 검색 결과를 근거로 실제 개인 자격 판정 완료를 주장할 수 없다. Render 판정 엔진의 상태도 별도로 확인해야 한다.

### E. 운영 DB 역할 확정

현재 회원 저장소는 Render PostgreSQL이다. Ncloud DB는 마지막 조회에서 비어 있었다. Render 유지 시 Ncloud DB를 반드시 채워야 하는 것은 아니다. Ncloud 이전을 선택할 때만 스키마·권한 적용, 백엔드 접속 변경, 기존 데이터 이전 및 검증이 필요하다. 스키마 파일 존재는 적용 완료와 다르다.

### F. 장애 대응과 보안·운영 마무리

CPU 구현이 있다는 사실과 자동 fallback은 다르다. GPU 타임아웃·과부하·버전 불일치에 대한 운영 추천 API의 처리는 미확인이다. 최종 UFW/기관 방화벽 정책, 외부 백업과 키의 분리 보관, 알림 전달, 복구 목표, 전체 재부팅 시험도 완료 증거가 부족하다. 인증서 발급·HTTPS는 확인했으나 `renew --dry-run` 성공과 timer 최종 출력은 확인되지 않았다.

## 7. 객관적 검증

1. 코드에 거리 계산·결측 마스크·버전 검사·인증·pool 분리 로딩이 존재한다.
2. 서버 응답에서 pool 9,000행·32차원과 준비 상태가 확인됐다.
3. CPU/GPU 표본 비교 및 외부 검색 응답이 제공됐다.
4. 로컬 전처리·추천 함수가 존재하므로 이를 일괄 ‘미구현’으로 분류하면 부정확하다.
5. Ncloud DB는 SQL 조회로 빈 상태가 확인됐고, 운영 회원가입은 Render로 연결되어 있다.

따라서 독립 GPU 서비스와 공개 검색 경로의 성과는 인정할 수 있다. 최종 추천 통합 완료는 인정할 근거가 부족하다.

## 8. 비판적 검증

- 네트워크 성공과 추천 성공은 다르다. health 200은 프로필 변환·판정·GPU 사용을 확인하지 않는다.
- 비교 집단은 가상 인구이고 출처 연령 범위도 제한적이다. 전체 연령·지역에서 유효하다는 일반화는 불가하다.
- k 상한 100은 응답 개수 상한이 아니다. 동점이 많으면 큰 응답과 집계 비용이 발생할 수 있다.
- 32차원과 파일 해시가 맞아도 전처리 코드·생년월일 매핑이 틀리면 의미가 다른 벡터가 전달될 수 있다.
- 추천 함수의 정책 해당 비율은 실제 수급 확률이 아니다. 입력이 적은 사용자에게 과도한 확신을 주지 않아야 한다.
- 18건 결과 일치로 성능 개선이나 추천 정확도를 주장할 수 없다. 현재 규모에서는 GPU 통신 비용이 이점을 상쇄할 수도 있다.
- 한 대씩인 서버와 SSH 터널은 장애 지점이다. 재시작 설정과 서비스 연속성 보장은 다르다.
- 운영 중인 Render 경로와 Ncloud 경로가 공존하므로, 화면 기능마다 백엔드가 달라지는 구성 혼선을 정리해야 한다.

## 9. 시간 제한 상황에서의 제출·시연 범위

정확히 주장할 수 있는 성과는 ‘L4 기반 CuPy KNN API 구축, 9,000행 32차원 로딩, 인증된 내부 호출, 표본 CPU/GPU 일치, EC2 HTTPS와 역방향 SSH 터널을 통한 검색 API 공개’다.

‘Render 가입자에게 GPU 기반 개인화 정책 추천을 제공한다’, ‘실제 자격을 판정한다’, ‘CPU 대비 성능 향상이 입증됐다’, ‘운영 준비가 모두 완료됐다’는 표현은 현재 증거로 사용하지 않는다.

향후 재개 시 순서는 운영 백엔드 역할 확정 → 프로필 변환 계약 대조 → 추천 요청 경로 연결 → 정책 해당 표·본인 판정 연결 → 사용자 흐름·장애·성능 평가다. 이 목록은 향후 작업이며 이번 문서 작성 중 구현하거나 배포하지 않았다.

## 10. 근거 목록

- 사용자 제공 서버 출력: GPU ready, CPU/GPU 18건 비교, TLS 401/403, 장애 502/200, 로컬 백업·복원 시험, EC2 터널·HTTPS·검색 응답, Ncloud DB 테이블 조회.
- 사용자 제공 운영 정보: Vercel 도메인, Render 백엔드 URL, NEXT_PUBLIC_API_BASE, Render PostgreSQL 사용.
- 확인한 로컬 코드: `backend/population/features.py`, `knn.py`; `outputs/gpu-knn-install`의 GPU API·로더·클라이언트·거리 코드.
- 데이터 메타데이터: `outputs/meta.json`의 인구 분할·특성·scale·출처·가정.

이 문서는 배포 완료 증거와 코드 존재를 구분한 현황 기록이며, 서버에 대한 변경 작업이나 추가 추천 구현은 포함하지 않는다.
